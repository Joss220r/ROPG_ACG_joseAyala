# Analisis comparativo: ROPC vs Authorization Code con PKCE

ROPC y Authorization Code con PKCE resuelven el mismo objetivo general, obtener un access token para consumir recursos protegidos, pero lo hacen con niveles de exposicion muy distintos. En ROPC, el cliente recibe directamente el usuario y password del propietario del recurso. Aunque el servidor guarde la contrasena con bcrypt y no la registre en logs, el cliente queda dentro del camino critico de las credenciales. Esto aumenta la superficie de ataque: un cliente comprometido, una captura mal redactada o un log accidental pueden exponer datos reutilizables. Tambien dificulta adoptar MFA o autenticacion sin contrasena porque el flujo espera que el cliente capture el secreto principal del usuario.

Authorization Code con PKCE separa mejor las responsabilidades. El usuario se autentica en el servidor de autorizacion, ve los scopes solicitados y aprueba el consentimiento sin entregar la contrasena al cliente. El cliente recibe un codigo temporal, vinculado al `redirect_uri`, al `client_id`, a los scopes y al `code_challenge`. PKCE reduce el riesgo de interceptacion del codigo porque un atacante que robe el `code` no puede canjearlo sin el `code_verifier` original. Ademas, el `state` permite que el cliente detecte respuestas que no pertenecen al flujo iniciado y reduzca el riesgo de CSRF.

En esta practica, ambos flujos emiten JWT con `iss`, `aud`, `exp`, `jti`, `client_id` y `scope`, y los recursos validan firma, expiracion y alcance. Sin embargo, la recomendacion final es usar Authorization Code con PKCE para aplicaciones modernas, especialmente clientes publicos web o moviles. ROPC debe quedar limitado a escenarios heredados y controlados, porque obliga a confiar demasiado en el cliente y no representa el modelo de autorizacion delegada mas seguro.
